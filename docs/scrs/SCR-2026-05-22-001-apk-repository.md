# SCR-2026-05-22-001 — Experimental signed APK repository

## 1. Context

Verity already publishes signed, attested container images and a static catalog
through GitHub Pages. Integer images are built from Wolfi/melange package
definitions, but consumers who want individual APKs currently have no stable
repository endpoint. An experimental APK repository lets early adopters install
Verity-built packages directly with `apk` while preserving a small operational
surface: static files, signed indexes, and the existing Pages deployment path.

This SCR defines the product and technical contract for that repository. It is
not an implementation change; implementation agents should use this document
and the linked stable docs as the source of truth for follow-up tasks.

## 2. Goals

- Publish a rolling `latest` APK repository alongside `verity.supply`.
- Support the MVP Alpine architectures: `x86_64` and `aarch64`.
- Serve a static, apk-compatible layout under `/apk/`:
  `/apk/<arch>/APKINDEX.tar.gz`, package files, and `/apk/verity.rsa.pub`.
- Sign every APK index with the Verity APK signing key.
- Document install, verification, retention, and key-rotation behavior before
  the repository is advertised as experimental.

## 3. Non-goals

- Versioned repository channels such as `stable`, `edge`, date snapshots, or
  per-release archives.
- Mirroring Alpine or Wolfi base repositories.
- Replacing OCI images, Helm wrapper charts, cosign image signatures, or SBOM
  attestations.
- Guaranteeing package ABI compatibility beyond package metadata generated by
  melange/apko.
- Supporting architectures beyond `x86_64` and `aarch64` in the MVP.

## 4. Scope

### In scope

- Repository layout and URL contract for the rolling `latest` repository.
- Signing-key custody, public-key publication, fingerprint documentation, and
  rotation procedure.
- Retention policy for superseded APK files and generated indexes.
- Install UX for Alpine-compatible clients.
- Verification workflow for repository metadata and package provenance.
- Implementation-task decomposition and dependencies.

### Out of scope

- Writing repository-generation code in this SCR PR.
- Adding production monitoring or SLA language for the experimental channel.
- Changing current image, chart, or catalog publication semantics.

## 5. Technical proposal

The repository is a static directory published by the existing GitHub Pages
deployment. The MVP layout is:

```text
/apk/
├── verity.rsa.pub
├── x86_64/
│   ├── APKINDEX.tar.gz
│   └── *.apk
└── aarch64/
    ├── APKINDEX.tar.gz
    └── *.apk
```

Each architecture directory is independently indexable and signed. Clients trust
the repository by installing `/apk/verity.rsa.pub` into `/etc/apk/keys/`, then
adding `https://verity.supply/apk/<arch>` to `/etc/apk/repositories`.

See `docs/architecture/apk-repository.md` for the steady-state contract and
`docs/guides/install-apk-repository.md` for user-facing installation steps.

## 6. Signing and key policy

- The private APK signing key is a GitHub Actions secret available only to the
  repository-publish workflow.
- The public key is committed or generated into the Pages artifact at
  `/apk/verity.rsa.pub` and documented with a SHA-256 fingerprint.
- Index signing fails closed: no unsigned `APKINDEX.tar.gz` is published.
- Rotation uses additive trust first: publish the new public key, sign new
  indexes with the new key, keep the old public key documented during the
  overlap window, then remove the retired key after the announced cutoff.

## 7. Retention

The MVP is rolling `latest` only. Pages contains the currently indexed packages
for each architecture plus its signed index. Superseded APKs are removed from
the published tree when they are no longer referenced by `APKINDEX.tar.gz`.
Build logs and intermediate artifacts may use normal GitHub Actions retention,
but they are not part of the repository contract.

## 8. Rollout plan

1. Land this SCR and stable docs.
2. Implement repository assembly for one package on a feature branch.
3. Add `x86_64` and `aarch64` matrix output, signed index generation, and Pages
   artifact staging.
4. Publish to a non-advertised `/apk/` path and verify install on fresh Alpine
   containers for both architectures.
5. Add links from the site/catalog only after verification is green.
6. Keep the channel labeled **experimental** until retention, rotation, and
   failure-recovery runs have been exercised at least once.

## 9. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Private signing key exposure | Store only as GitHub Actions secret; never commit private material; restrict publish workflow permissions. |
| Unsigned or stale index | Publish step validates signed index before Pages upload; fail closed on missing signature. |
| Architecture mix-up | Generate and validate each architecture directory independently; smoke-install from matching Alpine containers. |
| Broken rolling update | Stage repository into a temporary directory, verify, then atomically replace Pages artifact contents. |
| User confusion with production support | Label channel experimental in product docs, guide, and site copy until graduation criteria are met. |

   helper script first, then graduate into the CLI?
3. What package subset is allowed for the first experimental publish: all
   melange outputs or a curated allowlist?
